看右邊的綠色路徑：

### Slide 03: 為什麼網頁對話框 (Chatbot) 做不出完整軟體？
- **標題**：PARADIGM SHIFT｜為什麼網頁對話框 (Chatbot) 做不出完整軟體？
- **預估時長**：01:45
- **核心目標**：釐清「Web Chatbot」與「Agent IDE」的維度差距，點出檔案感知與終端執行的必要性。

#### 【畫面動作】
- 著重對比左邊「網頁聊天框的 4 大困境 (紅叉)」與右邊「AI Agent IDE 的 4 大超能力 (綠勾)」。

#### 【逐字稿】
這張投影片，是所有初學者最常踩中的痛點。
很多人一開始興致勃勃打開 ChatGPT 或 Claude 網頁版，輸入：「幫我寫一個排程工具」。
結果呢？AI 吐出一長串 500 行的程式碼。接著你就會陷入左邊列出的**四大困境**：
第一，它是單檔案片段。你不知道這段代碼該存成什麼檔名、放在哪裡；
第二，最嚴重的問題叫「**專案盲區 (Context Blind)**」。聊天框看不到你的整個資料夾，你讓它修 A 檔案，它一改就把 B 檔案相依的函式給刪了；
第三，**複製貼上地獄 (Copy-Paste Hell)**。程式跑出報錯，你複製錯誤訊息貼回去，它改了兩行，你又貼回來，來回 20 次，你已經忘記哪版代碼才是對的；
第四，它無法驗證。網頁對話框永遠沒辦法幫你按「執行」。

那右邊的 **AI Agent IDE** 到底差別在哪裡？
請大家記住四個詞：
1. **工作區全域感知**：Agent 能自動讀取整個資料夾的所有檔案、設定檔和資料庫 Schema，它對專案的全貌瞭若指掌。
2. **多檔案直接修改**：它可以一次性建立三、四個檔案，並精確修改其中某個檔案的第 50 到 60 行，不需要你動手複製。
3. **終端自主執行與自檢 (Self-Correction)**：它能直接在背景敲終端機指令（像是安裝套件、啟動伺服器、跑測試），看到報錯它會自己讀 Log、自己修正代碼！
4. **透明審閱**：它每次改動都會產出清晰的差異比較 (Diff)，你只需要審查、點擊接受。

這就是從「聊天玩具」到「生產力武器」的本質跨越！

### Slide 04: 拆解 AI Agent IDE 的工作引擎：非工程師如何駕馭它？
- **標題**：CORE MECHANISM｜拆解 AI Agent IDE 的工作引擎：非工程師如何駕馭它？
- **預估時長**：01:30
- **核心目標**：解釋 感知 (Context) ➔ 推理 (Reasoning) ➔ 行動 (Action) 三重閉環，確立人類指揮官地位。

#### 【畫面動作】
- 依序介紹上方 3 根支柱（01 感知引擎、02 推理大腦、03 執行工具箱），最後聚焦下方深色提示框。

#### 【逐字稿】
我們把 AI Agent IDE 的運作原理拆解成三個齒輪，這就是現代 AI 系統的閉環架構：

首先是 **01. 感知引擎 (Context Engine)**。
當你開啟工作區，Agent 會建立整個專案的索引。它知道有哪些檔案、使用的是 Python 還是 Node.js、有沒有設定檔。它就像走進你辦公室的助手，先看清桌上所有的公文夾。

第二是 **02. 推理大腦 (Reasoning Agent)**。
當你用中文說出一句話，例如「我想加一個匯出 Word 的功能」，大腦會開始思考：這需要安裝 `python-docx` 嗎？資料格式是什麼？函式該怎麼拆解？它會先生成一個嚴謹的執行計畫。

第三是 **03. 執行工具箱 (Action Tools)**。
想清楚之後，它不是嘴巴說說，而是直接拿出工具：自動寫檔、在終端下指令、執行代碼測試。如果測試失敗，這筆反饋又會回到感知引擎，由推理大腦再次思考並修復，直到成功為止。

**各位請看下方這個最重要的深色卡片：**
身為非工程師，你不需要去背任何程式碼語法！你的職責就是這三條：
第一：**描述痛點與期待成果**；
第二：**給出清楚的輸入、輸出與規則邊界**；
第三：**像主管一樣驗收**，看它做出來的成果符不符合你的業務直覺。

### Slide 05: 指導式 AI 開發心法：非工程師的四步交付法
- **標題**：METHODOLOGY｜指導式 AI 開發心法：非工程師的四步交付法
- **預估時長**：02:15
- **核心目標**：掌握 Problem Framing ➔ Spec-Driven ➔ Scaffolding ➔ Quality Gate 四大步驟，杜絕模糊指令。

#### 【畫面動作】
- 手指或游標橫向滑過 4 步卡片（Step 1 藍色 ➔ Step 2 紫色 ➔ Step 3 琥珀色 ➔ Step 4 綠色）。

#### 【逐字稿】
這張投影片，是今天整堂課最重要的心法架構，我們稱之為「非工程師的四步交付法」：

**第一步：Problem Framing（問題定義與場景拆解）**。
切記，不要為了用 AI 而用 AI。請挑選你日常工作中「頻率極高、規則明確、重複性大」的痛點。例如：每天早上整理待辦清單、每週整理訪視進度。把使用情境寫成一段話：誰要用？在什麼時候用？

**第二步：Spec-Driven（規格驅動，這是靈魂核心！）**。
千萬不要只對 Agent 丟一句：「幫我寫個排程軟體」，這樣做 AI 一定會隨意發揮。你必須給出具體的「**SPEC（規格書）**」：輸入長什麼樣？計算規則是什麼？輸出要什麼樣式？稍後下一頁我會教大家一份即插即用的規格模板。

**第三步：Scaffolding（漸進式搭架與模組化）**。
這是一條黃金原則——**先骨架，後血肉；先邏輯，後介面**。
很多初學者一上來就要求：「我要精美的 Web 介面加登入系統加後端資料庫加報表」，結果 Agent 一次做太多東西，直接崩潰死機。
正確的做法是切片：第一步先讓命令列跑通排程演算法；確認演算法對了，第二步再讓它存檔；第三步才給它加上漂亮的按鈕與網頁！每次只給一個具體任務。

**第四步：Quality Gate（人機協同品質閘門）**。
作為主管，你如何驗收？用邊界條件去考驗它：如果輸入時間衝突會怎樣？如果不小心輸入空值會不會當機？讓 Agent 自己寫測試驗證，最後由你人工審查簽核。

只要按照這四步走，你開發出來的軟體就會無比穩健、完全沒有幻覺。

### Slide 06: 非工程師的超能力：如何寫出一份高效 SPEC 規格書？
- **標題**：SPEC-DRIVEN METHOD｜非工程師的超能力：如何寫出一份高效 SPEC 規格書？
- **預估時長**：02:45
- **核心目標**：展示模糊 Prompt 的慘痛後果，傳授 Inputs / Rules / Outputs / Constraints 四要素與根目錄 `SPEC.md` 模板。

#### 【畫面動作】
- 先指出左上角紅色的「典型低效指令」，再對比左下角的「SPEC 四要素」，最後展示右邊黑底終端風格的 `SPEC.md` 模板。

#### 【逐字稿】
請大家看左邊這段紅字，是不是很眼熟？
「幫我寫一個每日排程工具，要很聰明、好用，可以排我的代辦事項，界面要好看。」
當你丟出這種提示詞，Agent 只能在黑暗中盲人摸象。它不知道你的工作是 15 分鐘一個週期還是 1 小時一個週期，不知道你有沒有固定會議，結果做出來的軟體你根本用不上。

所以，專業的非工程師，只用**結構化的 SPEC 四要素**跟 AI 溝通：
1. **Inputs（輸入）**：任務名稱、預估幾分鐘、截止時間、優先級、有沒有固定會議時間。
2. **Rules（邏輯規則）**：使用艾森豪矩陣排序；每天上限 8 小時；任務與任務之間自動預留 10 分鐘緩衝。
3. **Outputs（輸出）**：視覺化時間軸、超載警告標籤、一鍵複製 Markdown 晨報。
4. **Constraints（技術約束）**：請用單一 Python 檔案或輕量網頁，不要裝複雜的外部依賴，資料存本機就好。

大家請看右邊這張黑色的卡片，這是一份真實的 `SPEC.md`。
你只需要把這份簡單的文字檔放在專案資料夾根目錄，然後對 Agent 說：
**「請先仔細閱讀根目錄的 SPEC.md，並嚴格依照裡面的規範展開開發。」**

相信我，光是做這一個動作，Agent 理解你意圖的準確度，會直接提升三倍以上！因為你給了它唯一的行為標準。

- **標題**：WORKSHOP FOCUS｜實戰工作坊：打造你的專屬「每日任務智慧規劃器」
- **預估時長**：02:00

#### 【畫面動作】

#### 【逐字稿】
歡迎來到今天的實戰工作坊！我們要一起完成的專案，叫做「Daily Task Planner 每日任務智慧規劃器」。
大家每天上班是不是都有這種經驗？信箱裡有待回的信、主管隨口交代要趕的報表、下午又有固定的跨部門會議，腦袋一團混亂。

我們要讓 AI 幫我們打造一個 4 階段的自動化流水線：
- **階段 1：雜亂輸入層**。我們只要把今早隨手記的亂七八糟記事、會議時間貼進去，不需要刻意排版。
- **階段 2：智能萃取與分類**。系統會自動抓出每項任務的預估時間，並依照著名的「艾森豪四象限」自動分類：哪些是重要緊急（立刻做）、哪些是重要不緊急（安排專注時段）、哪些該授權或刪除。

很多非工程師在用 AI 時，最大的心理恐懼就是：**終端機突然跳出滿螢幕的紅色報錯！**

你不需要懂什麼 Traceback 或 IndexError。把終端機裡的紅字，從第一行到最後一行完整複製，貼回對話框，只要說一句：

如果你同時要資料庫、又要登入、又要發信，報錯時你會不知道哪裡壞了。此時告訴 Agent：「先不要管網頁，請寫一個純文字的 `test_calc.py`，只驗證排程計算邏輯，並印出每一步的計算日誌。」把問題隔離，大問題切成小驗證。

**法寶三：回歸規格約束（勒住 AI 幻覺的韁繩）。**
有時候 Agent 會太熱心，為了做一個小功能，自己安裝了一堆巨大又難搞的套件。這時你要勇於說不：「請不要安裝多餘的複雜依賴，請重新閱讀根目錄的 `SPEC.md`，使用 Python 最單純的寫法來實現。」

請大家看第二個案例：`D:\protocolwriter`。
在醫藥生技領域，臨床試驗計畫書 (Protocol) 是一份動輒 **50 到 100 頁**的巨型法規文件，必須嚴格符合 ICH E6、M11 與 ISO 14155 國際法規標準。

如果你嘗試用一般的 ChatGPT，給它一個 Prompt 叫它寫整本計畫書，保證會慘敗。
為什麼？因為單一對話框會遇到長度截斷；前面寫的收案條件，到了後面統計章節就忘光光、前後矛盾；最致命的是——**LLM 會偽造不存在的醫學論文與作者！** 這在法規上是絕對的死罪。

為了解決這個難題，我們在 `protocolwriter` 中指導 Agent 實現了 **Multi-Agent（多代理協同管線）**：
- 我們派出高智商的 **Planner Agent (Gemini Pro)**：專職萃取核心試驗設計，產出整套系統的定海神針——`Core Spec`。
- 專門的 **Literature Agent**：串接美國國家醫學圖書館 NCBI 的官方 **PubMed API**！每一篇參考文獻都必須即時連網驗證 PMID 與 DOI，代碼層級確保 100% 真實，杜絕任何論文捏造。
- 接著由多個 **Section Writers (Gemini Flash)** 平行獨立撰寫各章節，成本只要 Pro 的四分之一。
- 最後由 **Reviewer Agent** 進行跨章節嚴苛審查，有矛盾就打回修訂迴圈，審查通過後由組裝器封裝成 Word。

這套系統把過去專業團隊要寫三個月的計畫書初稿，在幾分鐘內高品質生成！

- **預估時長**：02:00

**規則 1：規格先行（Spec First, Code Later）**。
永遠不要第一句話就叫 Agent「開始寫 code」。先花 5 分鐘，把你的需求寫成 `SPEC.md`。磨刀不誤砍柴工，規格想清楚，程式碼一次就寫對。

**規則 2：小步快跑，拒絕巨石指令（Incremental Slices）**。
把一個大專案切成 3 到 5 個階段。核心邏輯跑通了 ➔ 驗證存檔 ➔ 再加前端 ➔ 再加匯出。一次只給一個任務，讓 Agent 專注解決單一問題。

像 ProtocolWriter 的 Core Spec 或 SASExamples 的 CDISC 一樣，核心資料結構必須統一管理，嚴禁在多個檔案中散落自相矛盾的定義。

**規則 4：做真實裁判，不當盲目看客（Human Reviewer in the Loop）**。
AI 寫程式非常快，但它不懂你們部門的潜規則與臨床真實需求。永遠用你的專業領域經驗去檢查產出，掌握系統的主導權。

**規則 5：善用終端與報錯作為溝通橋樑（Logs are Friends）**。
看到紅字報錯，不要害怕！完整複製 Log 貼給 Agent，把它當成你的溝通橋樑，讓 AI 快速自我修復。
